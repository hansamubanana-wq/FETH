作業ブランチ: `claude/multiplayer-race-performance-abz9i0`（`main` と同一地点）

## 1. 何が起きていたか / 何を直したか

報告された症状は「大人数でプレイするともう一度レースが行われたり固まったり重い」。
原因は独立した3つ。さらに修正の過程で1つ回帰を出して、それも直した。

### (A) 重い → レースを重ねるほど悪化して最後は固まる

**原因: `Race.stop()` がどこからも呼ばれておらず、3Dシーンが1レースも解放されていなかった。**

ローカル対戦を3レース連続で回してGLオブジェクトの生存数を数えた実測値:

| | 1レース後 | 2レース後 | 3レース後 |
|---|---|---|---|
| 修正前 テクスチャ / バッファ | 26 / 1351 | 53 / 2708 | 81 / 4071 |
| 修正後 テクスチャ / バッファ | 5 / 23 | 5 / 23 | 5 / 23 |

オンラインは延々とレースが続くので、10レースも回ればGL資源が1万個超。スマホなら確実に固まる。

直した内容（`src/race.js` / `src/race3d.js` / `src/raceui.js`）:

- 再生完了時と中断時に `Race.stop()` を呼ぶ
- `Race3DRenderer.dispose()` をシーン全体の解放に作り直した
  （ジオメトリ・マテリアル・テクスチャ・InstancedMeshのインスタンス行列・
  スキンメッシュのボーンテクスチャ・ライトのシャドウマップ）
- **`WebGLRenderer` は canvas につき1つを使い回す**（`getSharedRenderer()`）。
  レースごとに作り直すと three が内部に持つ既定テクスチャ等がレンダラーの数だけ
  GLコンテキストに積み上がり、`renderer.dispose()` では消えない
- 馬のGLBを1回だけ読んでキャッシュ（`loadHorseGltf()`）。毎レースのパースとGPU転送をなくした
  - 注意: `SkeletonUtils.clone()` はジオメトリを、clone したマテリアルはテクスチャを
    オリジナルと共有する。`markShared()` で印を付けて解放対象から除外している。
    **ここを外すと2レース目以降で馬が消える**
- `resize()` が毎フレーム `canvas.width` に代入して描画バッファを作り直していたのをやめた
  （サイズが変わったときだけ適用）

### (B) レースがもう一度行われる / ベット画面で固まる

**原因: ホストのフェーズ移行に多重実行の防止がなかった。**

締め切り直後にスナップショットが連続で届くと `hostStartBetting()` が二重に走り、
`horseSeed` が引き直される。すると送信済みの `betDone` が false に戻されるのに、
ベット画面の再表示条件がラウンド番号だけだったため画面が出ず、全員が待機画面で停止していた。

直した内容（`src/online.js`）:

- ラウンド単位の「予約票」(`claimOnce` / `releaseClaim`) でホストのフェーズ移行を1回に固定
  （ベット開始・レース開始・精算・リセット。書き込み失敗時は返却して `scheduleHostRetry()` で再試行）
- ベット画面の表示判定をラウンド番号から「馬立て(`round:horseSeed`)＋実際に表示中か」に変更
- 再生中にラウンドが進んだら `stopRacePlayback()` で古いレース映像を中断して資源を解放
- 締め切り後・次ラウンド開始後のベット送信は捨てる

### (C) 大人数での重さ（Firestore の設計）

**原因: ホストだけが players を購読し、全員分の買い目込みの状態を
`rooms/{code}.summary` に書き戻して配っていた。**

- 誰か1人がベットするたびに部屋ドキュメントを丸ごと書き直す
  → Firestore の「1ドキュメントあたり毎秒1書き込み」の目安を超えて詰まる
- 配信量が人数の2乗で増える（N人分の買い目 × N人へ配信）
- ホストが1台でも重いと全員の進行が止まる

**Firebase を別サービスに替える必要はなく、データモデルの問題だった。**

直した内容:

- 全端末が `rooms/{code}/players` サブコレクションを直接購読する方式へ変更。
  書き込みは各自1件、部屋ドキュメントへの書き込みは1ラウンド3回で人数に依存しない
- 結果画面・プレイヤー一覧・フレンド一覧・画面切替を、内容が変わったときだけ描き直す
  （`el.dataset.sig` による差分判定、`showScreen()` の早期リターン）
- レース中のライブ表示を innerHTML 作り直しからノード更新に変更。
  順位が変わらないフレームは人数分の精算計算ごと省く。大人数時は更新間隔を 130ms→280ms に
- 着順の再計算(`orderFromSeed`)をシードでキャッシュ
- Firestore のリスナーエラーを握りつぶさずログに出す

### (D) 【回帰】賭けられないレースが毎ラウンド始まる ← (C) の副作用

(C) で `summary` をやめて部屋ドキュメントと players を**別々のリスナー**にしたことで発生。

`hostStartBetting()` は「部屋ドキュメント(`phase=betting`, `round+1`)」と
「各プレイヤーの `betDone=false`」を同じバッチで書く。バッチはアトミックだが、
**2つのリスナーへの到着順は保証されない**。部屋ドキュメントが先に届くと:

> 「今は round R+1 のベット中」＋「全員 betDone=true（前ラウンドの残骸）」

→ `allBet()` が true → `hostStartRace()` が即発火 → 誰も賭けていないレースが1本走る。

以前は phase もプレイヤー状態も同じ `summary` フィールドにあったので食い違わなかった。

直した内容（`src/online.js`）:

- `o.playersVersion` を数え、ベット開始後に players を1回でも受け取るまで `allBet()` を信用しない
  （`scheduleBetAdvance()` の `playersFresh`）
- プレイヤードキュメントに `round` を持たせ、前ラウンドの `betDone` を「まだ賭けていない」扱いに
  （`isCurrentRound()`。`round` を持たない旧ドキュメントは現行扱いにして、
  更新途中の部屋が2分の締め切りまで進まなくなるのを避けている）
- 自分の状態が前ラウンドのままの間はベット画面を切り替えない
- ベット開始の書き込みから漏れた場合の自力復帰（`scheduleBetSelfHeal()`、2.5秒後）

## 3. 未検証・残っている懸念（ローカルで見てほしいところ）

**クラウド実行環境の制約で、実 Firestore を使ったオンライン検証だけができていない。**
Firestore の WebChannel（長時間接続）がサンドボックスのプロキシを通らず、
ブラウザから外部サイトにも到達できなかった。未変更の `main` でも同じだったので
変更由来ではないが、結果として以下は**実機未確認**:

1. **実 Firestore での複数端末プレイ**
   → ローカルなら `node scripts/verify-online-rounds.mjs 3 2` が回せるはず。
   画面遷移の回数がラウンド数と一致するかを機械判定する（多い=やり直し、少ない=固まり）

2. **`scripts/verify-online-scale.mjs`** を新方式に合わせて書き直したが未実行。
   部屋ドキュメントへの書き込みが人数に依存しないことを確認するもの

3. **ホスト交代（ホストが退出したとき）の挙動**。
   `claimOnce` の予約票はクライアントごとのローカル状態なので、
   新ホストは予約票を持たずに引き継ぐ。ラウンド跨ぎでは問題ないはずだが実機未確認

4. **再生が遅い端末の扱い**。ホストは自分の再生完了後に精算し、結果は10秒で次へ進む。
   10秒以上遅れている端末はレース映像が途中で打ち切られる（従来からの挙動）。
   大人数だとここが気になるかもしれない

5. 旧バージョンで作られた進行中の部屋は、プレイヤードキュメントに `round` がない。
   互換のため「現行扱い」にしているので (D) の保険が1ラウンドだけ効かない可能性がある。
   部屋を作り直せば解消

## 4. さわるときの注意

- バージョンは `src/version.js` と `sw.js` と `index.html` のバッジの**3か所**にある。
  デプロイのたびに `APP_BUILD` を1つ上げる（更新バナーの検知に使う）
- **検証で本番の `meta/version` を書き換えないこと。** `APP_BUILD` が
  Firestore の `meta/version` より大きいと、オンライン画面を開いた瞬間に書き込まれ、
  まだデプロイしていないビルド番号が全ユーザーに更新バナーとして出る。
  デプロイ前にテストするなら `APP_BUILD` を一時的に現行値へ戻して実行する
- Service Worker が `vendor/firebase` を先読みキャッシュしている。
  Playwright の `page.route()` は SW 経由の取得を差し替えられないので、
  スタブを使うテストでは `newContext({ serviceWorkers: "block" })` が必須
- 3Dの資源解放で `markShared()` の除外を外すと、使い回している馬のGLBまで
  解放されて2レース目以降が壊れる
- Vercel は `main` への push で本番へ自動デプロイ。問題が出たら
  Vercel ダッシュボードから前のデプロイへロールバックできる
